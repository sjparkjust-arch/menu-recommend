밥픽의 주요 기능을 다섯 가지 영역으로 정리했습니다.

첫째, 계정 관리. Django 기본 인증을 그대로 쓰지 않고 커스텀 유저 모델을 설계해, 개인별 선호 음식 정보를 안전하게 관리합니다.

둘째, 맞춤형 추천 엔진. 별도 모듈 recommender.py에 로직을 모아, 점심·저녁·BEST·실시간 인기·취향, 성격이 다른 다섯 카드를 서로 중복 없이 뽑습니다. '취향' 카드는 가입 때 고른 취향과 평점 기록에, 나와 입맛이 겹치는 사용자의 고평점 메뉴에 가중치를 주는 협업 필터링까지 결합한 개인화 추천입니다.

(여기서 홈페이지를 열어 실제 대시보드를 보여드리겠습니다.)

셋째, 식사 기록 및 통계. 메뉴와 식사 기록을 1대 다 관계형 DB로 모델링해, 캘린더 히스토리와 요리 종류별 섭취 비율을 시각화합니다.

넷째, 리뷰 및 인터랙션. 새로고침 없이 즉시 반응하는 AJAX 좋아요, 세션 기반 '최근 본 메뉴' 추적, 실시간 인기 순위를 구현했습니다.

마지막, 외부 미식 콘텐츠 연계. 유튜브·미슐랭·블루리본을 대시보드에 큐레이션해 먹을거리와 볼거리를 한 화면에서 제공합니다.

밥픽의 기술 스택은 크게 네 계층입니다.

백엔드는 Python과 Django로 추천 알고리즘·사용자 인증·서버 로직을 구현했습니다.

프런트엔드는 HTML·CSS와 바닐라 자바스크립트로, 좋아요 비동기 처리와 돌림판·사다리 캔버스 게임까지 직접 구현했고, 반응형·다크모드 UI를 완성했습니다.

데이터베이스는 두 가지입니다. 영속 데이터는 MariaDB로 관리하고, 세션·캐시는 Redis에 분리 저장합니다. 이 '세션 분리'가 뒤 확장성 설계의 핵심입니다.

그리고 오늘 강조하고 싶은 인프라. 리눅스 위에 Nginx와 Gunicorn을 올려 실제 서비스가 가능한 배포 환경을 직접 구성했습니다.

[전환] "본격적인 인프라 이야기에 앞서, 두 명이 작업을 어떻게 나눴는지 짧게 짚고 넘어가겠습니다."

밥픽의 인프라 아키텍처입니다.

우측 다이어그램처럼 웹·앱 서버와 DB를 물리적으로 분리한 3계층 구조입니다. Server 1에는 Nginx·Gunicorn·Django를, Server 2에는 MariaDB와 Redis를 올렸습니다.

앞단의 Nginx는 443 포트에서 암호화를 풀고 정적 파일을 직접 처리하는 문지기입니다. 동적 요청만 WSGI인 Gunicorn을 거쳐 Django로 전달되고, Gunicorn은 데몬으로 등록해 서버가 꺼져도 자동으로 되살아납니다.

특히 처음부터 확장성을 고려했습니다. 세션을 앱 메모리가 아니라 Redis에 분리 저장해, 앱 서버를 수평 확장해도 로그인 상태가 유지되는 무상태 구조입니다. 시크릿 키와 DB 정보는 .env로 분리했습니다.

이 표준화된 설계 덕분에 코드를 고치지 않고도 AWS의 EC2·RDS로 무중단 이관할 수 있는 로드맵을 갖췄습니다.

[전환] "그럼 이 인프라를 실제로 어떤 단계를 거쳐 구축했는지, 배포 일지로 보여드리겠습니다."
📖 용어 뜻 (발음) ›
  • 3계층 / 3-Tier (쓰리 티어)웹·앱·DB를 계층으로 나눈 구조.
  • WSGI (더블유에스지아이)웹 서버와 파이썬 앱을 연결하는 표준 규격. Gunicorn이 그 역할.
  • 데몬 (Daemon · 데몬)백그라운드에서 계속 도는 프로그램.
  • systemd (시스템디)데몬을 관리하고 자동 재시작해 주는 리눅스 도구.
  • 무상태 (Stateless · 스테이트리스)상태(세션)를 앱 서버에 저장하지 않는 구조. 서버 증설이 자유로움.
  • 수평 확장 (Horizontal Scaling)서버 대수를 늘려 부하를 나누는 것.
  • .env (닷 이엔브이)비밀번호·주소 같은 설정값을 담는 환경변수 파일.
  • AWS · EC2 · RDS (에이더블유에스 · 이씨투 · 알디에스)아마존 클라우드. EC2=서버, RDS=관리형 데이터베이스.

📜 전체 대본 펼치기 ›

1단계, runserver. 동시 접속 한계, 터미널 끄면 죽고, 주소 뒤 :8000이 붙어 실서비스엔 부적합.

2단계, WSGI 서버 Gunicorn. 워커 3개로 동시 요청 처리, systemd 데몬 등록으로 자동 재시작. Nginx와는 TCP 포트가 아니라 유닉스 소켓으로 통신 — 같은 서버라 더 빠르고 안전.

3단계, 앞단에 Nginx. 정적 파일은 Nginx가 직접 서빙해 부하를 줄이고, HTTP 표준 80번 포트에 띄워 :8000을 URL에서 없앴습니다.

4단계, HTTPS 전환. 80→443 자동 리다이렉트, 사설망이라 자체 서명 인증서를 발급하되 SAN에 IP를 명시. Nginx가 암호화를 풀고 Django엔 평문으로 넘기므로 SECURE_PROXY_SSL_HEADER와 CSRF_TRUSTED_ORIGINS를 맞춰줘야 무한 리다이렉트·403이 안 납니다.

결과적으로 브라우저→Nginx→유닉스 소켓→Gunicorn→DB로 이어지는 완전한 프로덕션 배포 파이프라인을 완성했습니다.

[전환] "이 과정이 순탄치만은 않았습니다. 가장 큰 도전 두 가지는 한빈 팀원이 이어서 소개하겠습니다."
📖 용어 뜻 (발음) ›
  • runserver (런서버)장고 기본 개발용 서버. 실서비스엔 부적합.
  • Gunicorn (구니콘)실서비스용 파이썬 앱 서버.
  • 워커 (Worker · 워커)요청을 처리하는 일꾼 프로세스. 3개면 동시에 3개 처리.
  • systemd (시스템디)서버가 꺼져도 자동 재시작하게 관리하는 도구.
  • 유닉스 소켓 / .sock (유닉스 소켓 · 닷 삭)같은 서버 안 프로그램끼리 빠르고 안전하게 통신하는 통로.
  • TCP 포트 (티씨피 포트)네트워크 통신용 번호. 소켓과 대비되는 방식.
  • HTTP / HTTPS (에이치티티피 · 에이치티티피에스)웹 통신 규약 / 그 암호화된 버전.
  • 리다이렉트 (Redirect · 리다이렉트)다른 주소로 자동 이동(80→443).
  • 자체 서명 인증서 (Self-signed Certificate)공인기관 없이 직접 만든 HTTPS 인증서. 내부망용.
  • SAN (에스에이엔, 흔히 "샌")인증서에 유효한 도메인·IP를 명시하는 항목.
  • SECURE_PROXY_SSL_HEADER (시큐어 프록시 에스에스엘 헤더)"앞단이 HTTPS로 받았다"를 장고가 믿게 하는 설정.
  • X-Forwarded-Proto (엑스 포워디드 프로토)Nginx가 장고에게 "원래 HTTPS였다"를 알려주는 값.
  • CSRF_TRUSTED_ORIGINS (씨에스알에프 트러스티드 오리진스)이 주소에서 오는 폼 요청은 믿겠다는 보안 설정. (CSRF=위조 요청 공격)
  • 403 에러 (사공삼)권한 거부 오류.
