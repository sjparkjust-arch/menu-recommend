주요 기능 및 외부 연계

박상준

밥픽의 주요 기능을 다섯 가지 영역으로 정리했습니다.

첫째, 계정 관리입니다. Django 기본 인증을 그대로 쓰지 않고 커스텀 유저 모델을 설계해, 개인별 선호 음식 정보를 안전하게 관리합니다.

둘째, 맞춤형 추천 엔진입니다. 뷰가 아니라 별도 모듈(recommender.py)에 로직을 모아, 점심·저녁·오늘의 BEST·실시간 인기·취향, 성격이 다른 다섯 개 카드를 서로 중복 없이 뽑습니다. 그중 '취향' 카드는 가입 때 고른 취향과 그동안의 평점 기록을 바탕으로, 여기에 나와 입맛이 겹치는 사용자의 고평점 메뉴에 가중치를 주는 협업 필터링까지 결합한 개인화 추천입니다.

셋째, 식사 기록 및 통계입니다. 메뉴와 식사 기록을 1대 다 관계형 DB로 모델링해, 일자별 캘린더 히스토리와 요리 종류별 섭취 비율을 시각화함으로써 지속적인 방문(리텐션)을 유도합니다.

넷째, 리뷰 및 인터랙션입니다. 페이지 전체를 새로고침하지 않고 즉시 반응하는 AJAX 좋아요, 세션 기반 '최근 본 메뉴' 추적, 평점 기반 실시간 인기 순위를 구현했습니다.

마지막으로 외부 미식 콘텐츠 연계입니다. 유튜브 리뷰와 미슐랭·블루리본 칼럼을 대시보드에 함께 큐레이션해, 먹을거리와 볼거리를 한 화면에서 제공합니다.

📖 용어 (읽는법 · 뜻)
  • Django Auth(장고 어스)장고의 기본 로그인·회원 인증 기능.
  • 커스텀 유저 모델기본 회원 정보에 취향 등 필요한 항목을 더한 우리만의 회원 모델. (영어: Custom User Model)
  • recommender.py(리코멘더 파이)추천 로직만 따로 모아둔 파이썬 파일.
  • 협업 필터링나와 입맛이 비슷한 사람이 좋아한 메뉴를 추천하는 방식. (영어: Collaborative Filtering)
  • AJAX(에이잭스)새로고침 없이 서버와 데이터를 주고받는 기술. 좋아요가 즉시 반영되는 이유.
  • 세션로그인 사용자 정보를 서버가 잠시 기억하는 것. '최근 본 메뉴'에 사용. (영어: Session)
  • 리텐션사용자가 떠나지 않고 다시 방문하는 것(재방문율). (영어: Retention)

사용된 기술 스택

박상준

밥픽의 기술 스택은 크게 네 계층입니다.

백엔드는 Python과 Django로, 추천 알고리즘과 사용자 인증, 서버 로직 같은 핵심 기능을 구현했습니다.

프런트엔드는 Django 템플릿 위에 HTML·CSS와 바닐라 자바스크립트로, 좋아요 같은 비동기 처리와 돌림판·사다리 같은 캔버스 게임까지 직접 구현했고, 데스크톱·모바일에 대응하는 반응형과 다크모드 UI를 완성했습니다.

데이터베이스는 두 가지를 씁니다. 메뉴·사용자·리뷰·식사 기록 같은 영속 데이터는 MariaDB로 무결성을 관리하고, 로그인 세션과 캐시는 Redis에 분리해 저장합니다. 이 '세션 분리'가 바로 뒤에서 말씀드릴 확장성 설계의 핵심이 됩니다.

그리고 오늘 가장 강조하고 싶은 인프라입니다. 로컬 개발에 그치지 않고, 리눅스 위에 Nginx와 Gunicorn을 올려 실제 서비스가 가능한 배포 환경을 직접 구성했습니다.

[전환 → 6] "본격적인 인프라 이야기에 앞서, 이 작업을 저희 두 명이 어떻게 나눠 진행했는지 짧게 짚고 넘어가겠습니다."
📖 용어 (읽는법 · 뜻)
  • Python / Django(파이썬 / 장고)파이썬 = 프로그래밍 언어, 장고 = 파이썬 웹 프레임워크.
  • 바닐라 자바스크립트외부 프레임워크 없이 순수 자바스크립트만 쓴 것. (영어: Vanilla JavaScript)
  • Canvas(캔버스)브라우저에서 그림·애니메이션을 그리는 기능. 돌림판·사다리 게임 구현에 사용.
  • Bootstrap(부트스트랩)화면 디자인을 빠르게 잡아주는 CSS(씨에스에스) 도구.
  • MariaDB(마리아디비)표(관계형) 형태로 데이터를 저장하는 데이터베이스.
  • Redis(레디스)메모리에 저장해 아주 빠른 저장소. 세션·캐시용.
  • Nginx(엔진엑스)맨 앞에서 요청을 받는 웹 서버.
  • Gunicorn(구니콘)파이썬 앱을 실제로 돌리는 앱 서버. '지유니콘'이라고도 읽음.
  • Linux(리눅스)서버 운영체제.

시스템 아키텍처 및 확장성 ⭐

박상준

밥픽의 인프라 아키텍처입니다.

우측 다이어그램처럼, 저희는 웹·앱 서버와 DB를 물리적으로 분리한 3계층 구조로 설계했습니다. 실제로 Server 1에는 Nginx·Gunicorn·Django를, Server 2에는 MariaDB와 Redis를 올려 두 대의 서버로 나눴습니다.

가장 앞단의 Nginx는 443 포트에서 암호화를 풀고 정적 파일을 직접 처리하는 문지기 역할을 합니다. 동적 요청만 WSGI인 Gunicorn을 거쳐 Django로 전달되고, 이 Gunicorn은 데몬으로 등록해 서버가 꺼져도 자동으로 되살아나도록 안정성을 확보했습니다.

특히 저희는 처음부터 확장성을 고려했습니다. 로그인 세션을 앱 메모리가 아니라 Redis에 분리 저장했기 때문에, 앞으로 앱 서버를 여러 대로 수평 확장하더라도 어느 서버로 요청이 가든 로그인 상태가 그대로 유지되는 무상태(Stateless) 구조입니다. 또 시크릿 키와 DB 접속 정보는 .env로 분리해 환경만 바꾸면 그대로 이관되도록 했습니다.

이 표준화된 3계층 설계 덕분에, 코드를 고치지 않고도 트래픽이 늘면 AWS의 EC2·RDS로 무중단 이관할 수 있는 로드맵을 갖추게 됐습니다.

[전환 → 8] "그럼 이 인프라를 실제로 어떤 단계를 거쳐 구축했는지, 로컬 개발부터 HTTPS 배포까지의 과정을 배포 일지로 보여드리겠습니다."
📖 용어 (읽는법 · 뜻)
  • 3계층 / 3-Tier(쓰리 티어)웹·앱·DB를 계층으로 나눈 구조.
  • WSGI(알파벳 그대로)웹 서버와 파이썬 앱을 연결하는 표준 규격. Gunicorn이 그 역할.
  • 데몬백그라운드에서 계속 도는 프로그램. (영어 Daemon — '데몬'으로 읽음)
  • 무상태(스테이트리스)세션 같은 상태를 앱 서버에 저장하지 않는 구조. 서버 증설이 자유로움. (영어: Stateless)
  • 수평 확장서버 대수를 늘려 부하를 나누는 것. (영어: Horizontal Scaling)
  • .env(닷 + 알파벳 그대로 e·n·v)비밀번호·주소 같은 설정값을 담는 환경변수 파일.
  • AWS · EC2 · RDS(전부 알파벳 그대로 · 2는 "투")아마존 클라우드. EC2=서버, RDS=관리형 데이터베이스.
8

실전 배포 일지 — 4단계 ⭐

박상준

1단계, 개발 환경 runserver. 처음엔 다들 아는 런서버로 시작했습니다. 하지만 동시 접속 처리에 한계가 있고, 터미널을 끄면 서버도 같이 죽습니다. 무엇보다 주소 뒤에 :8000 포트가 붙어 실제 서비스용으로는 부적합했습니다.

그래서 2단계, 운영용 WSGI 서버 Gunicorn. 워커를 3개 띄워 동시 요청을 처리하고, systemd 데몬으로 등록해 서버가 꺼져도 자동 재시작되게 했습니다. 특히 Nginx와의 통신에 TCP 포트가 아니라 유닉스 소켓(.sock)을 썼는데, 같은 서버 안의 통신이라 소켓을 쓰면 네트워크 스택을 거치지 않아 더 빠르고 안전합니다.

3단계, 그 앞에 Nginx를 세운 것. 무거운 정적 파일은 파이썬까지 가지 않고 Nginx가 직접 서빙해 앱 부하를 줄였습니다. 여기 재미있는 포인트가 있는데요 — 평소 웹서핑할 때 주소 뒤에 포트를 안 치시죠? Nginx를 HTTP 표준 80번 포트에 띄웠기 때문에 브라우저가 이를 자동 인식해서, 지저분한 :8000을 URL에서 없앨 수 있었습니다.

마지막 4단계, HTTPS 전환. 80번으로 들어온 요청을 443으로 자동 리다이렉트하고, 사설망이라 자체 서명 인증서를 발급하되 최신 브라우저 규격에 맞춰 SAN에 IP를 명시해 인증서 에러를 막았습니다. 그리고 Nginx가 암호화를 풀고 뒤의 Django엔 평문으로 넘기기 때문에, Django 쪽에도 두 가지 설정을 맞춰줘야 했습니다. 하나는 "앞단에서 이미 HTTPS로 처리됐다는 걸 신뢰하라"는 설정, 다른 하나는 "우리 서비스 주소에서 들어온 요청은 안전한 것으로 인정하라"는 보안 설정입니다. 이 짝을 안 맞추면 주소가 끝없이 도는 무한 리다이렉트나 로그인할 때 권한 거부(403) 에러가 터지는데, 저희는 여기까지 완벽히 동기화했습니다. ※ 이 두 설정의 실제 이름 (SECURE_PROXY_SSL_HEADER·CSRF_TRUSTED_ORIGINS)은 발표 때 그대로 읽지 말고 위처럼 '뜻'으로 설명하세요. 정확한 이름은 아래 용어에 있습니다.

결과적으로, 브라우저에서 Nginx, 유닉스 소켓, Gunicorn을 거쳐 DB까지 이어지는 완전한 프로덕션 배포 파이프라인을 완성했습니다.

[전환 → 9, 한빈님에게] "물론 이 과정이 순탄치만은 않았습니다. 저희가 구축 과정에서 겪은 가장 큰 도전 두 가지는, 이어서 한빈 팀원이 소개해 드리겠습니다."
📖 용어 (읽는법 · 뜻)
  • runserver(런서버)장고 기본 개발용 서버. 실서비스엔 부적합.
  • Gunicorn(구니콘)실서비스용 파이썬 앱 서버.
  • 워커요청을 처리하는 일꾼 프로세스. 3개면 동시에 3개 처리. (영어: Worker)
  • systemd(시스템디)서버가 꺼져도 자동 재시작하게 관리하는 도구.
  • 유닉스 소켓 / .sock(유닉스 소켓 · 닷 삭)같은 서버 안 프로그램끼리 빠르고 안전하게 통신하는 통로.
  • TCP 포트(TCP는 알파벳 그대로)네트워크 통신용 번호. 소켓과 대비되는 방식.
  • HTTP / HTTPS(알파벳 그대로)웹 통신 규약 / 그 암호화된 버전.
  • 리다이렉트다른 주소로 자동 이동(80→443). (영어: Redirect)
  • 자체 서명 인증서공인기관 없이 직접 만든 HTTPS 인증서. 내부망용. (영어: Self-signed Certificate)
  • SAN("샌" 또는 알파벳 그대로)인증서에 유효한 도메인·IP를 명시하는 항목.
  • SECURE_PROXY_SSL_HEADER(발표에선 읽지 말고 "뜻"으로 설명)본문에서 말한 "앞단 Nginx가 HTTPS로 받았다는 걸 신뢰하라"는 설정의 실제 이름.
  • X-Forwarded-Proto(엑스 포워디드 프로토)Nginx가 장고에게 "원래 HTTPS였다"를 알려주는 값.
  • CSRF_TRUSTED_ORIGINS(발표에선 읽지 말고 "뜻"으로 설명)본문에서 말한 "우리 서비스 주소에서 온 요청은 안전하게 인정하라"는 보안 설정의 실제 이름. (CSRF=위조 요청 공격)
  • 403 에러(사공삼)권한 거부 오류.

[도전 1] 데이터 이관과 마이그레이션 진단

최한빈

첫 번째 위기는 DB 서버를 물리적으로 분리한 직후 찾아왔습니다.

데이터 복원 후 마이그레이션을 실행했더니, Django가 "컬럼이 중복되었습니다(Duplicate column)" 하고 멈췄습니다. 에러가 터진 곳은 파이썬 코드 실행 단이었습니다.

그래서 먼저 데이터가 유실됐는지 확인했고(정상), 코드와 DB 이력을 대조해 보니 마이그레이션 파일 계보가 불일치함을 발견했습니다. 마지막으로 SHOW COLUMNS로 실제 스키마를 확인해 보니, DB 스키마는 이미 최신인데 django_migrations 기록만 빠져 있었습니다. 알고 보니 문제는 Django에서 일어난 것처럼 보였지만, 실제로는 DB 내부의 이력 데이터(0002_add_column)가 손상됐던 것입니다.

여기서 엔지니어링 판단이 필요했습니다. 구글링하면 --fake 옵션으로 넘기라는 글이 많지만, 무작정 쓰면 지금은 넘어가도 나중에 더 큰 장애를 유발합니다. 그래서 컬럼 단위로 스키마 일치를 완벽히 검증한 뒤에만 해결했습니다.

이를 통해 '증상이 발생한 계층(Django)과 실제 원인이 있는 계층(DB)은 다를 수 있다'는 값진 교훈을 얻었습니다."

[도전 2] 온프레미스의 한계와 AWS 도입 명분

최한빈

두 번째 위기는 IP 변경으로 인한 연쇄 장애입니다.

서버 분리를 위해 네트워크를 변경하면서 DB 서버 IP가 .73에서 .78로 끝자리 하나 바뀌었습니다. 그런데 IP 하나가 바뀌자, MariaDB 권한 거부부터 방화벽, .env, Nginx, SSL 인증서까지 무려 5개 계층이 도미노처럼 무너졌습니다.

DB 계정이 단순 아이디가 아니라 '아이디 + 접속 IP'의 세트라는 것을 파악하고, 하위 네트워크부터 최상위 보안까지 계층 순서대로 5단계를 다시 설정해 복구했습니다.

  1. DB 계정 권한 재설정 — 새 IP에 GRANT 재부여 후 FLUSH PRIVILEGES.
  2. OS 방화벽(ufw) 갱신 — 기존 룰 삭제 후 새 IP에만 3306 오픈.
  3. 애플리케이션 .env 수정 — DB_HOST 주소 업데이트.
  4. Nginx 리버스 프록시 갱신 — 프록시 타겟 IP 수정 후 reload로 무중단 반영.
  5. SSL 인증서 SAN 재발급 — openssl.cnf의 SAN에 새 IP 반영해 재발급·재적용.

이 고생을 통해 온프레미스 인프라가 IP에 얼마나 강하게 결합되어 있는지 뼈저리게 체감했고, 역설적으로 이 시행착오가 고정 엔드포인트를 제공하는 AWS RDS와 클라우드로 넘어가야 할 강력한 기술적 명분을 쥐여 주었습니다."

프로젝트 기대 효과 및 마무리

공동 (한빈·상준)

밥픽은 사용자의 메뉴 선택 스트레스를 덜어주고, 쌓이는 데이터(기록·리뷰)를 바탕으로 추천이 점점 정교해지는 데이터 선순환 구조를 만들어 갈 것입니다. 추후에는 재방문율(DAU), 추천 메뉴 클릭률(CTR) 같은 지표로 비즈니스 성과도 증명해 나갈 예정입니다.

저희는 이번 프로젝트를 통해 단순히 프론트엔드와 백엔드를 잇는 코딩을 넘어, Nginx와 Gunicorn을 설정하고, 서버 장애의 진짜 원인을 추적하며, 클라우드 확장의 필요성을 몸소 증명해 냈습니다. 코드를 짜는 것을 넘어, 서비스를 안정적으로 사용자에게 전달하는 인프라의 중요성을 깊이 이해하게 된 시간이었습니다.

앞으로도 문제를 회피하지 않고 근본 원인을 파헤치는 끈기 있는 엔지니어로 성장하겠습니다.

[각자 프로젝트 후기 한마디]

최한빈: 웹 서비스를 시작할 때 웹 구성부터 개발까지 이렇게 어려운지 몰랐고, 시간이 정말 빠르게 지나간 것 같습니다. 인프라 구축을 바닥부터 해 보니 간단한 구축도 쉽지 않았는데, 실무는 얼마나 더 어려울지 걱정 반 기대 반입니다.

박상준: 저는 추천 로직과 UI, 그리고 인프라를 맡았는데, 웹 서비스 하나를 실제로 세상에 띄우는 일이 이렇게 여러 계층으로 이뤄져 있는지 이번에 처음 체감했습니다. 처음엔 runserver 하나면 끝인 줄 알았는데, Gunicorn과 Nginx, HTTPS까지 직접 쌓아 올리면서 '돌아가는 코드'와 '서비스되는 코드'는 다르다는 걸 배웠습니다. 특히 서버 IP 한 자리가 바뀌자 여러 계층이 도미노처럼 무너지는 걸 겪으며, 클라우드가 왜 필요한지를 말이 아니라 몸으로 이해하게 됐습니다. 아직 부족하지만, 문제를 회피하지 않고 끝까지 원인을 파고드는 개발자가 되고 싶습니다.

이상으로 '밥픽' 발표를 마치겠습니다. 경청해 주셔서 감사합니다!

💬 예상 질문 대비 (공용)

Q. '취향' 추천이 정말 협업 필터링인가요?

네. 나와 같은 메뉴에 고평점을 준 사용자들이 좋아한 메뉴에 가중치 3배를 주고, 여기에 개인의 요리 종류 선호도(1배)를 합산해 점수가 높은 메뉴를 뽑습니다. 데이터가 쌓일수록 정교해지는 협업 + 콘텐츠 기반 하이브리드입니다.

Q. 왜 클라우드가 아니라 온프레미스부터 했나요?

클라우드가 추상화로 숨기는 웹서버·WSGI·소켓·TLS의 원리를 직접 손으로 구성해 이해하기 위해서입니다. 그 경험이 있어야 클라우드로 갈 때 무엇을 왜 옮기는지 판단할 수 있다고 봤습니다.

Q. 동시 접속은 어떻게 처리하나요?

Gunicorn 워커 3개로 병렬 처리하고, 세션을 Redis로 분리해 앱 서버를 수평 확장할 수 있게 설계했습니다. 트래픽이 늘면 워커 수를 늘리거나 앱 서버를 추가하면 됩니다.

Q. 왜 TCP 포트가 아니라 유닉스 소켓을 썼나요?

Nginx와 Gunicorn이 같은 서버에 있어, TCP 루프백보다 네트워크 스택 오버헤드가 없어 더 빠르고, 파일 권한으로 접근을 통제할 수 있어 더 안전합니다.

Q. 왜 --fake로 간단히 넘기지 않았나요?

--fake는 당장은 성공한 것처럼 보여도 스키마와 이력이 어긋난 채 봉합돼 나중에 더 큰 장애를 부릅니다. 그래서 컬럼 단위로 실제 스키마 일치를 검증한 뒤에만 이력을 맞췄습니다.

Q. 무상태(Stateless)가 왜 수평 확장에 중요한가요?

세션이 특정 앱 서버 메모리에 있으면 그 사용자는 그 서버로만 가야 합니다. 세션을 Redis로 공유하면 어느 앱 서버가 받아도 되므로, 앱 서버를 자유롭게 늘릴 수 있습니다.

실제 프로젝트 코드(recommender.py·인프라 설정)와 최한빈·박상준 대본을 대조해 정리했습니다.
